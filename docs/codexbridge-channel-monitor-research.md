# CodexBridge 多人 AI 与渠道监控接入评估

分析日期：2026-11-06。源码基线：`Gan-Xing/CodexBridge` 提交 `92166e02f4c7c8fcc0d223e894dd33664db754ea`，提交时间为2026-06-07。不是对线上运行状态或最新稳定版本的保证。

用户已明确：普通微信好友直发做不了可以跳过；可改为每个人接入 AI，由 AI 回答渠道监控问题。权限采用“管理员分别分配，每人只看获准渠道”。本报告按这一替代目标设计，不再把公众号消息当作好友私聊。

## 结论

CodexBridge 有可借鉴的微信机器人收发、会话路由和 AI 回复实现，适合作为会话入口候选；不应直接以原版共享 Codex 实例向多人开放。需要补齐身份绑定、渠道权限、线程隔离和受限工具执行。

推荐先做两名模拟用户、两个模拟渠道的只读原型，再安排用户明确指定的少量真实扫码和问答验收。先支持“列出我的渠道”“查询余额”“哪些渠道低于阈值”“读数何时更新”；主动告警作为另一个验收项，不能从一次回复成功推导为全天候主动推送可用。

“每人一个AI”在产品上可以是独立会话、记忆和权限；不需要为每个人训练一套模型。共享模型服务不等于共享聊天、文件、数据权限或账单额度。

## 接入结构

```text
甲的微信机器人会话 → 绑定身份甲 → 甲的独立AI会话 ┐
乙的微信机器人会话 → 绑定身份乙 → 乙的独立AI会话 ├→ 受权限约束的只读查询接口 → 当前渠道监控快照
管理员分配/撤销权限 ─────────────────────────────┘
```

当前飞书机器人仍是渠道数据的唯一采集方，沿用 `ChannelMonitorController.state()`、`onChange` 与成功读数回调。不要再启动另一套浏览器登录去采集同一批渠道，也不把管理员平台令牌给 AI。

建议新增独立的本机查询接口或受控 IPC。接口本身根据可信身份校验权限，然后只返回获准字段；AI不能读取全量数据后自行决定哪些可以展示。

若只做这几类查询，优先保留 CodexBridge 的微信通信与路由层，把普通用户的执行入口收紧为指定查询工具。不要直接把完整远程编程助手的所有命令暴露给查询用户。如果继续使用 Codex app-server，需要独立受限执行环境；单独工作目录、`read-only` 或不同 threadId 均不等于租户级数据隔离。官方 app-server 文档提供审批、沙箱及动态工具能力，但租户授权仍需应用负责。

## 每个人如何接入

1. 管理员在本机建立接入档案，勾选此人允许查看的渠道。未分配时默认无权限。
2. 按平台实际允许的扫码/绑定流程，让本人完成机器人会话连接并发送一次绑定请求。适用账号、是否每人单独 botAccount、是否能共用入口均须现场核验，不能假设同一二维码可无限多人复用。
3. 从已验证的入站消息取得 `(platform, botAccountId, senderId)`，管理员确认其对应档案。昵称、自报姓名、输入他人的ID不能作为绑定依据。
4. 为该主体分配独立线程、记录与额度；服务端保存身份到渠道权限的绑定。
5. 对话时只查询该主体获准的渠道。撤销权限后立即拒绝新的查询和发送；重置或裁剪含已撤销资料的旧模型上下文，不能只修改下一次工具返回。

少量试点可评估独立机器人账号配独立 worker、状态目录及会话；若多个 worker 仍是同一操作系统用户并能读全盘，它们依然没有完整安全隔离。规模扩大后需要账号管理器、路由命名空间和并发限制，不能简单在共享 JSON 目录启动多个写入进程。

## 交互范围

| 用户请求 | 首版拟定行为 |
| --- | --- |
| “我有哪些渠道？” | 只列获准渠道，无权限时提示管理员分配，不列出其他渠道名称 |
| “余额还有多少？” | 返回获准快照，注明原单位和最后成功时间；不同单位不相加 |
| “哪些低于提醒线？” | 只在获准且有效读数范围内比较，失败读数不当作0 |
| “为什么显示未取得？” | 按状态说明待登录/读取失败/过期，不让AI猜具体网站故障 |
| “给我看某个未授权渠道” | 接口拒绝；AI不能自行扩大权限 |
| “帮我充值、登录、改权限” | 首版不提供这些操作，指向管理员处理 |
| “今天消耗了多少/余额走势” | 当前渠道监控没有经本次验证的连续历史账本，不凭当前余额推算历史；作为后续独立需求 |

查询默认读现有快照，不能每次聊天都触发真实网页刷新。刷新频率、失败退避仍由原监控模块控制；过期时如实告知。

## 拟定只读接口契约

本节是设计草案，未实现。建议仅监听本机回环地址或使用受 ACL 保护的 IPC；异机部署另行设计 TLS、身份认证及数据最小化。

- `GET /v1/me/channels`：列当前主体被允许查看的渠道。
- `GET /v1/me/channels/{channelId}/snapshot`：返回该渠道最近快照及有效性状态。
- `GET /v1/me/alerts`：查看该主体获准范围内的告警状态。
- 接口认证：由桥接器根据已校验的入站账号/发送者生成短期、限定主体与用途的凭证；AI不能指定或覆盖主体，不把凭证放入用户提示词。
- 输出白名单：`channelId`、`displayName`、`metric`、`value`、`unit/display`、`status`、`checkedAt`、`successAt`、`stale`、`threshold`。名称和备注也作不可信数据，不执行其中的指令。
- 接口必须在返回前重新验证权限版本；发送队列出队时再核验，处理撤权、重绑和慢响应。金额过期或读取失败时标未知，区分当前与上次成功值。
- 首版固定少量渠道无需分页；按主体限制频率、队列长度、每日AI额度和回复长度。超限返回明确状态；只读接口暂时失败可有界退避，外部消息发送结果不明不能自动重放。
- 密钥、Cookie、网页HTML、账号密码、创建账本、其他用户聊天与完整错误响应均不进入查询结果、模型上下文或普通日志。

## 方案取舍

| 路线 | 匹配度 | 实现与维护 | 主要边界 |
| --- | --- | --- | --- |
| 原版共享Codex直接给多人用 | 有聊天能力，但权限不符合要求 | 初装少、风险和后续整改大 | 线程可共享、权限可切换、凭据明文等未收紧，不采用 |
| 复用微信通信层，新增身份权限和受限查询AI | 最符合本次目标 | 中等，需要接入档案、查询接口及验收 | 推荐先做两人模拟原型，再验证真实绑定 |
| 每人独立完整Codex环境 | 适合每个人都需要通用编程助手 | 运行成本、环境隔离与维护较高 | 对只查余额需求偏重；独立目录不足以隔离 |
| n8n分发通知 | 适合规则编排 | 多一个部署和状态节点 | 不能代替对话身份、数据权限和微信会话资格，暂不引入 |
