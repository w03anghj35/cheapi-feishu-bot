# 渠道监控多渠道通知与 n8n 选型

调研日期：2026-11-06。状态：方案分析与现有代码回归完成；新增通知能力未实施、未真实发送。用户已澄清：要由普通微信账号直接给微信好友发私聊，不接受用公众号通知替代。

## 需求澄清与修订结论

后续替代目标：用户允许普通微信好友直发不合适就跳过，并提出通过 CodexBridge 给每个人连接 AI 查询渠道监控；已选择管理员按人分配可见渠道。见 [CodexBridge 多人接入评估](codexbridge-channel-monitor-research.md)。下述好友直发方案保留为此前分析，不代表仍必须实施。

2026-11-06：此前把“普通微信通知”理解成个人在公众号里收提醒，偏离需求。公众号推送与 ClawBot 会话均不作为本需求的实现方案。下文保留它们仅供区分产品边界，不再推荐用于首版。

目标链路应为“渠道余额告警 → 本机微信发送模块 → 已明确绑定的好友私聊”。n8n 只能承担上层编排，不能因此获得个人微信好友的发送权限。此次核对的微信移动分享 SDK 和 PC OpenSDK 文档未确认可在服务端无人值守地指定普通好友并发消息的公开接口；不能把分享给会话能力当成自动私聊接口。[S13,S14]

可进一步评估 Windows 微信客户端界面自动化：在登录会话中定位已确认好友、填写告警、发送并核对会话结果。当前仅为候选设计，需验证实际客户端版本、同名好友辨识、窗口遮挡/锁屏、会话失效、失败暂停及重启去重；无法保证长期稳定或账号零风险。微信协议8.2.1.6对未经授权第三方自动化有明确限制，不能把客户端自动化称作官方允许的机器人API。[S15]

未选择现成 wxauto 包作为生产实现：本次读取的项目 README 声明面向微信3.9.X，并明确禁止实际生产及商业用途，不能仅看到它有UIAutomation能力就直接引入。[S16] 不建议以注入、Hook或私有协议作为当前告警系统的默认路线。后续原型先用虚构内容验证会话定位，不发送真实消息；真实好友发送需由用户明确指定账号、好友与测试内容后另行进行。

## 目标与建议

面向本机管理员，让现有五站余额监控通过普通微信好友私聊、QQ 邮箱和手机短信提醒。核心流程限定为低余额通知、每日余额汇总、管理员显式测试通知。首版先保留现有采集与邮件，验证好友私聊发送的可行性，再决定是否增加客户端发送模块；短信在明确接收内容和服务商资格后接入。复杂路由出现后，再接独立 n8n 服务。

本次不安装 n8n、不修改运行中的业务、不发送真实消息。成功标准是形成可实施的选择、接口边界和验收清单，而非声称多渠道已上线。

## 现有项目的接入基础

- `key-tool/main.js` 的 `ChannelMonitorController.onResult` 把读数交给 `channelAlert.observed`，已有明确接入点。
- `key-tool/channel-alert.js` 同时包含阈值判定、低值区间去重、每日调度、加密存储、消息内容及 QQ SMTP 发送，适合逐步拆出发送适配器，不宜直接把全部逻辑搬到 n8n。
- 当前 `send` 依赖可注入，但配置、目标身份、存储和界面都以邮箱为中心；仅替换发送函数还不能构成可靠的多渠道支持。
- 现有邮件逐收件人发送；低余额只接受成功读取，五站按各自原单位比较。每日汇总使用北京时间与读数时效检查。发送前持久化尝试，结果不明不自动重发。
- 运行时仍依赖本机桌面程序持续工作。把通知分发放到服务器，不会自动让本机浏览器在关机后继续采集。

## n8n 能解决什么

n8n 是可视化工作流平台，支持自托管或托管服务，可以把事件接收、条件分支、外部接口和执行记录连接起来。[S1]

与本需求直接相关的是 Webhook 触发器、SMTP Send Email、HTTP Request 和错误工作流。[S2–S5] 可用 Webhook 接收本机告警，再按事件类型和严重程度选择推送服务。邮件有通用节点；微信和国内短信可以通过服务商 API 接入，但仍须开通账号、绑定接收方并满足服务商要求，不能从“有 HTTP 节点”推导为“所有微信场景开箱即用”。

建议学习它的发送适配器、条件路由和执行记录思路。当前不需要复制 n8n 源码、内嵌其编辑器或引入 AI 节点。若日后需要值班表、不同人员路由、多级升级、多个系统共用通知规则，独立部署 n8n 的收益才会明显提高。这是基于当前项目规模的工程判断，未做 n8n 性能或长期稳定性实测。

许可证为 Sustainable Use License，并对企业版文件另行限制。许可证允许自身内部业务、个人或非商业用途；不是可任意转售的 MIT/Apache 许可。若以后分发包含 n8n 的收费产品、向客户提供托管编排或使用企业版功能，需按实际商业模式重新核对授权。[S6] 本次只参考公开文档与设计，没有复制其代码或素材。

## 微信、邮件、短信的具体路线

| 接收方式 | 候选接法 | 优点 | 主要限制与待验证项 |
| --- | --- | --- | --- |
| 公众号通知（不符合本次需求） | PushPlus 公众号推送 | HTTP 接口较直接 | 不等于用户账号给好友私聊；不作为首版实现 [S7] |
| 插件会话（不作为替代） | PushPlus 微信 ClawBot | 服务商有文字推送说明 | 没有验证可由用户账号任意指定好友发送；不作为首版实现 [S12] |
| 普通微信好友私聊（本次目标） | 评估本机客户端界面自动化 | 目标会话形式符合需求 | 未验证客户端兼容、身份绑定与长期运行；受平台自动化条款约束，不宣称已可用 [S13–S16] |
| 企业微信 | 内部群机器人/消息推送 | 官方群通知接入路径，适合作备用 | 腾讯文档说明外部群不支持该群机器人方式；存在发送频率限制，不能当作任意普通微信群接口 [S10] |
| QQ 邮箱 | 沿用现有 QQ SMTP | 已有配置、队列、去重、日报与测试按钮 | 当前仓库真实投递尚待验收；SMTP 接受不等于最终收件 |
| 手机短信，仅催看提醒 | PushPlus 短信渠道 | 接入较少、适合提示去查看告警 | 官方当前说明只能固定内容提示，不能带自定义内容和链接，且需付费 [S8] |
| 手机短信，含渠道和余额 | 云短信，例如阿里云 SendSms | 可按审核模板填写允许的变量 | 需可用账号及审核通过的签名、模板；业务内容能否通过须实际审核，不保证个人账号一定满足条件；发送计费且需核对回执 [S9] |

好友私聊方案需先实测发送端登录、锁屏与窗口状态、准确好友定位、文字发送和结果不明时停发。不能只看到按钮被点击就宣称消息送达。QQ 邮箱指邮件，不是 QQ 聊天消息。

## 方案比较

以下成本、稳定性与可维护性是工程评估，并非压测或真实用户反馈。

| 方案 | 匹配度/保留优点 | 主要缺陷 | 实现与维护复杂度 | 稳定性边界 | 隐私与许可 |
| --- | --- | --- | --- | --- | --- |
| 现有程序直接接适配器 | 当前最匹配；复用已有监控和发送状态 | 新服务商需代码适配 | 首版较低；渠道增多后上升 | 少一个中转服务，仍依赖本机和服务商 | 凭据本机加密；推送服务会处理必要内容，遵守其条款 |
| 现有程序 + 独立 n8n | 适合后续复杂规则；可视化编排和统一执行记录 | 多一个常驻服务、存储、升级与故障点 | 中等；需要跨进程状态和去重设计 | 必须验证分支失败、重启及重放；n8n 停机影响经它转发的通知 | 增加数据副本和凭据管理；受 SUL/企业版边界限制 |
| 全部通知经单一聚合平台 | 原型较快，多个渠道共用接口 | 平台故障可能同时影响多个通知入口；短信内容受限 | 较低到中等；受平台变化影响 | 多入口不等于独立故障域 | 通知与目标资料经过聚合平台；遵守额度/计费/隐私条款 |

保留现有邮件作为独立路径，微信与短信尽量避免全部绑定在同一个上游。暂不选完整嵌入 n8n，因为当前主要需要发送能力，尚未提出可视化工作流编辑需求。

## 建议结构与状态边界

```text
现有渠道读取 → 告警规则与持久事件 → 按目标分别投递并记录
                                 ├─ QQ SMTP
                                 ├─ 普通微信好友私聊（客户端方案待验证）
                                 ├─ 短信服务
                                 └─ 可选：n8n Webhook → 经批准的扩展流程
```

规则归属：本机负责读数有效性、原单位阈值、低值区间和日报时间；若启用 n8n，它负责约定的投递路由，避免两边同时重新判断阈值和生成日报。

建议事件字段：`schemaVersion`、`eventId`、`eventType`、`sourceId`、`sourceName`、`metric`、`value`、`unit`、`observedAt`、`severity`、`recipientRef`。低余额事件按一次低值区间固定 ID；日报按北京时间日期固定逻辑身份。不得每次网络重试新建事件 ID。只发必要业务摘要，不传登录密码、Cookie、平台令牌或浏览器内容。

每个“事件 + 通知方式 + 接收方”独立保存状态，建议区分待发送、尝试中、服务商已受理、送达已确认、明确失败与结果不明。服务商无送达证明时不能伪造“已送达”。一个渠道失败不能触发整条流程重跑并重复发送其他成功渠道。

接收 n8n Webhook 时，HTTP 2xx 可以只表示工作流启动，不应直接让所有分支变为已发送。持久去重需要原子占位与唯一约束，不能用“先查询再插入”两个无保护节点应对并发。远端发出后、回执保存前崩溃仍可能结果不明，不能承诺 exactly-once。结果不明先查状态；明确未受理的暂时错误才考虑有限退避。

若通过 n8n 分发同一目标，该目标不能又在本机直发。短信可以作为严重告警的独立规则；如果要“没看到微信再发短信”，还需明确的人工确认入口，接口受理/送达回执均不能证明用户已读。

新增设置建议统一为“通知设置”：分别启停微信、邮箱、短信；每项提供脱敏目标、独立测试按钮、最近状态与错误提示。事件类型支持低余额和日报；恢复通知、失联告警、不同严重等级属后续可选范围。短信默认关闭，配置每日上限和冷却间隔。

## 接口契约草案

这是实施前约定，尚未联调；具体凭据只能由管理员在本机密码框或服务端凭据管理页输入。

| 接口 | 方法与地址结构 | 认证/关键字段 | 回执与验证 | 分页、限流与重试 |
| --- | --- | --- | --- | --- |
| 现有邮件 | TLS SMTP `smtp.qq.com:465` | SMTP AUTH；发件邮箱、授权码、单个收件人、主题、正文 | 替身测试确认 accepted 包含该目标；再实测收件箱 | 无分页；本机串行；未知结果不重发 |
| PushPlus | POST `https://www.pushplus.plus/send/` | 请求体 token；title、content、channel 等 | 返回流水号后查询最终结果；手机验收 [S7,S11] | 发送无分页；按账户当前额度/频率限制节流；未知结果不重放 |
| n8n 可选入口 | POST `https://<自有主机>/webhook/<固定路径>` | Header Auth 等正式认证；仅传白名单事件字段 | 生产 URL 与测试 URL 分开；持久受理与各目标回执分开验证 [S2] | 本接口设计为单事件，无分页；限流与去重自行配置，不假定 n8n 自动提供业务幂等 |
| 企业微信备选 | POST `https://qyapi.weixin.qq.com/cgi-bin/webhook/send?key=<本机秘密>` | Webhook key；msgtype、text/content 等按正式文档核对 | 核对业务回执并在授权群验收；具体实现前复核接口文档 | 无分页；腾讯当前说明每机器人20条/分钟 [S10]；未知结果不重放 |
| 阿里云短信候选 | HTTPS POST `https://dysmsapi.aliyuncs.com/`，SDK 操作 SendSms | 官方签名认证，最小权限凭据；PhoneNumbers、SignName、TemplateCode、TemplateParam | 校验 Code、BizId，查询发送详情或处理回执，再核对手机 [S9] | 单条发送无分页；详情查询另按文档分页；遵守账号/号码限制并加本地预算。官方明确短信不支持幂等，超时先查回执 |

实施时限制目的地址、HTTPS 证书校验、超时与响应体大小。n8n 如异机运行需保护入口和执行记录；凭据不要放入流程导出 JSON，正文也应按最小必要原则保存。普通推送平台的服务协议、隐私协议与账号实际权益要在启用前再次核对；本次未完成签约或商业使用资格验证。

## 实施顺序与验收

1. 第一阶段：保留邮件行为；先验证普通微信客户端能否准确定位明确指定的好友，以虚构内容做不发送的原型检查，再决定发送适配器与目标状态实现。旧邮件配置、暂停状态和不明记录必须保持兼容。
2. 第二阶段：在用户明确指定发送账号、好友和测试内容后，执行少量真实测试；核对好友私聊与 QQ 收件。按需审核短信模板、明确预算，验收一个授权手机号。
3. 第三阶段：确有复杂分流需求时部署 n8n，先用模拟 Webhook/发送器证明重启、并发重复和单分支失败不会导致重复投递。

待实现的测试清单：首次配置/缺配置、无读数/旧读数、阈值相等、重复触发、连续低值与恢复、慢发送不漏其他来源、部分渠道失败、超时后已实际受理、重复回调、重启保留不明记录、配置变更/暂停、存储损坏、权限不足、平台限流、短信预算、窄屏与键盘操作、秘密不进日志。此清单是模拟场景计划，不是已收集的真实用户反馈。

本次实际验证：`npm test` 451/451 通过；`npm run check` 112 份脚本通过；`npm run check:release` 150 个索引文件通过。发布检查只检查 Git 索引，不能覆盖工作区全部未暂存或未跟踪文件。测试证明当前代码基线，不证明新增推送已可用。没有部署 n8n、没有新增账号、没有实际微信/短信发送、没有重启在线程序。
